# Creative Script Validation Service

A small service that checks an advertising script before it goes into production.

You give it two things: the **campaign brief** and the **script** written against it. It gives back
a scorecard with three scores, the reasoning behind each one, and — the important part — a
fact-check of every product claim in the script against the actual product manuals.

Built around THE FACE SHOP (TFS) product training decks.

Live: https://script-validator-737435708170.asia-northeast3.run.app

## Why three scores

A script can fail in three different ways and they don't overlap, so I score them separately:

1. **Brief alignment** — does it do what the brief asked? Right audience, key message, mandatory
   inclusions, tone, CTA. A well-written script that ignores the brief should score low here.
2. **Marketing message quality** — is it good copy? Hook, clarity, persuasiveness, tone, CTA.
   Judged on its own, ignoring the brief and ignoring whether the facts are right.
3. **Product claim validity** — are the factual claims actually true? This is the one with real
   legal risk (false advertising), and it's the reason the system needs RAG at all. Every claim
   gets checked against retrieved manual text, not against what the LLM thinks it knows.

Each prompt explicitly says what *not* to judge, otherwise the three scores collapse into one
vague "is this good" number.

## How it works

Two pipelines.

**Ingestion (run once, offline):**

```
manifest.json -> load PDFs/PPTXs -> chunk -> embed -> Supabase (pgvector)
```

The manuals are PowerPoint training decks, not manuals in the usual sense. A slide is already a
small self-contained topic, so **one slide = one chunk** — no fixed-window splitting. Only pages
over the size limit get split on paragraph boundaries, which in practice almost never happens.
Tables are pulled out too (a lot of the certification and ingredient claims only live in tables).

`manifest.json` lists which files to ingest and gives each one a clean product name, since the
original filenames are things like `2018-11_Dr__Belmeur_Advanced_(Ampoule_added).pptx`. Files not
in the manifest are skipped.

Re-running ingestion is safe: each chunk has a sha256 of its text, and chunks already in the
database are skipped instead of re-embedded.

Current corpus: **554 chunks across 42 products** (every file in the Drive folder except three
legacy `.ppt` files and one brochure PDF that turned out to be scanned images with no text layer).

**Scoring (per request):**

```
brief + script
  -> parse_brief()          structure the brief into fields
  -> extract_claims()       pull out the checkable claims
  -> retrieve_for_claims()  one vector search per claim
  -> coverage report        how well-grounded each claim is
  -> 3 scoring calls
  -> scorecard
```

The retrieval is done **per claim**, not once for the whole script. Searching with an entire ad
script as the query gives mushy results. One query per claim means each claim gets its own
evidence and its own verdict, with the source chunk id attached so you can go check it.

5 LLM calls per request. Everything else is vector math or plain Python.

## Retrieval evaluation

The assignment asked for retrieval accuracy after every run, so there are two parts to this.

**Offline baseline** (`python -m scripts.run_eval`): 40 questions generated by an LLM from known
chunks, so the correct answer chunk is known. Current numbers:

```
Recall@5 = 0.825    MRR = 0.702    (40 queries, 42-product corpus)
```

25 of 40 were rank 1. The interesting part is the 7 misses: **all 7 landed on a different slide of
the correct product deck**, and none went to the wrong product. Decks repeat themselves a lot, so
the retrieved slide usually says nearly the same thing as the expected one. For claim checking,
what matters is whether the right product's evidence comes back, and on that measure it was 40/40.

An earlier run on a 17-product subset scored 0.875 / 0.711 with 1 cross-product miss. Tripling the
corpus cost 5 points of exact-chunk recall but removed the cross-product error, which is the
trade I would want.

It's a synthetic benchmark — questions written *from* the chunk they're meant to find — so treat it
as an upper bound and a regression check, not proof of real-world accuracy.

**Per run**: there's no ground truth at request time, so instead each claim reports the similarity
of its best-matching chunk and gets flagged `well_grounded` or `low_confidence`. This appears in
every scorecard. It matters because it separates *"this claim is false"* from *"we couldn't find
the right section of the manual"* — a low-confidence claim gets the verdict `unverifiable`, not
`unsupported`.

The 0.68 threshold was picked by hand from test claims: real matches scored 0.74+, unrelated
nonsense scored around 0.58, and made-up claims about products not in the corpus scored ~0.62.
It would need re-tuning if the embedding model or the corpus changed.

## Scoring rules that aren't the LLM's call

A couple of things are deliberately plain code, not prompt instructions, so they're predictable:

- If more than half the claims come back `unverifiable`, the validity score is capped at 5.
- If a script makes **no** checkable claims, the validity axis is dropped from the overall score
  instead of counting as 10/10. Saying nothing isn't the same as being accurate.
- Overall = 0.3 brief + 0.3 quality + 0.4 validity (validity weighted highest — it's the axis with
  actual brand and legal risk), renormalised if an axis is excluded.
- A brief that can't be parsed into any usable field is rejected with a 422 rather than scored.

## Stack

| | |
|---|---|
| API | FastAPI |
| LLM | Groq, `openai/gpt-oss-120b` |
| Embeddings | Gemini `gemini-embedding-001`, 768 dims |
| Vector store | Supabase (Postgres + pgvector) |
| Hosting | Google Cloud Run |
| Parsing | PyMuPDF (pdf), python-pptx (pptx) |

No LangChain or LlamaIndex. The corpus is small and bounded, and the retrieval logic is about 40
lines of SQL and Python, so a framework would have been more code to understand, not less.

**On swapping providers:** all LLM calls go through `app/clients/llm_client.py` and all embedding
calls through `app/clients/embedding_client.py`. Nothing else in the codebase imports a provider
SDK. This got tested for real — the project ran on Z.AI GLM, then Gemini, then Groq, and each
switch was three lines in `.env` and zero code changes. Any OpenAI-compatible endpoint works.

## Running it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # then fill in the keys
uvicorn app.main:app --reload
```

Then open http://127.0.0.1:8000 — there's a form with a "Load example" button.
API docs are at `/docs`.

Database setup (once): run `app/db/schema.sql` in the Supabase SQL editor. It enables pgvector and
creates the two tables.

To ingest manuals: drop the files in `data/manuals/`, list them in `data/manuals/manifest.json`,
then `POST /ingest`. The decks aren't committed — they're confidential training material and 280MB.

### Endpoints

| | |
|---|---|
| `GET /` | the form |
| `POST /score` | brief + script -> scorecard |
| `POST /ingest` | rebuild the vector store from `data/manuals/` |
| `GET /health` | health check |

## Logging

Logs go to stdout as JSON so Cloud Logging can index the fields. Every scoring run is also written
to a `score_runs` table with the inputs and the full scorecard as jsonb, so any run can be looked
up or replayed later. If that insert fails the request still succeeds — the user already has their
scorecard, a database hiccup shouldn't turn that into a 500.

## Known limitations

- **Claims aren't scoped to a product.** The extractor returns a product name as free text
  ("Alltimate PDRN Hyalu 7 Serum") which doesn't match the internal slug
  (`alltimate_pdrn_hyalu_7_serum`), so retrieval searches all products. It still lands on the right
  deck almost every time, but scoping would make it stricter. Needs a name-to-slug resolution step.
- **3 old `.ppt` files are skipped.** Legacy binary format, no clean Python reader, would need
  LibreOffice to convert. They're 3 of 46 and all old.
- **Section type tagging is keyword matching**, not classification, and it's rough — over half the
  chunks end up tagged `spec`. It's only metadata, nothing depends on it being right.
- **Scores move a little between runs** on identical input, even at temperature 0.1. The claim
  verdicts are stable; the numbers drift by a point.
- **Re-running ingestion won't pick up chunking or tagging changes**, because the content hash is
  unchanged. You'd need to clear the table first.
- **Identical slides across decks are stored once.** The dedup hash is of the text only, so a
  boilerplate slide repeated in several decks keeps the product name of whichever deck was ingested
  first. Only affects boilerplate in practice, but hashing product name + text would be the fix.
- **Email and MCP interfaces aren't built.** Everything goes through one `run_pipeline(brief,
  script)` function and the HTTP route is a 3-line adapter over it, so another interface would be
  a thin wrapper — but I didn't have time to build them, so I'm not claiming they exist.

## Layout

```
app/
  clients/      llm + embedding wrappers (the only files that talk to a provider)
  db/           pgvector store, run logs, schema.sql
  models/       all the pydantic shapes
  pipeline/     ingestion, retrieval, brief parsing, claim extraction, scoring, eval, report
  routers/      /score and /ingest
  static/       the form
  utils/        json logging
scripts/        smoke test + eval runner
data/
  manuals/      manifest.json (the decks themselves are gitignored)
  eval/         eval dataset + latest eval report
```
